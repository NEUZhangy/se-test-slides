Why do we test? Because people write bugs.

Mistake

A mismatch nobody noticed.

The template defined 21 inputs. The sensor code supplied 20.

Defect

The mistake lands in the code.

read input[20]

Failure

Users see it.

8.5 million PCs show a blue screen.
Why not just read the code carefully?
Reading checks what you thought of. Bugs live in what you didn't.
Code changes every day. Yesterday's careful read is out of date.
Testing means executing software on purpose to find failures before users do.Many definitions also count reviews and static analysis as testing (static testing).

What is testing for?

Find bugs before users do

A bug in the lab is cheap. A bug on a million phones is not.

Build it right, and build the right thing

Verification checks the code matches the spec. Validation checks the product meets what users actually need.

Change code without fear

A test suite is a safety net. Refactor, then run it.

Know when to ship

Tests lower risk. They never prove zero bugs.

What makes a test good?

A good test…

  • Fails when the behavior breaksand only then
  • Gives the same result every runno timing, no shared state
  • Runs fast enough for every change
  • Checks one thing, and says what broke
  • Survives a refactortests behavior, not internals

Measure it: mutation testing

Plant small bugs (mutants) in the code. Good tests kill them.

M1likes += 1 → likes += 2Killed
M2not in → inKilled
M3likes -= 1 → likes += 1Killed
M4delete liked_by.discard(user)Exercise: ?
3 / 4mutation score: M4 survives
No test checks that a user can like again after unliking. Add: like, unlike, like → count is 1.
Tools: mutmut (Python), Stryker (JS/TS), PIT (Java)
pstack

Test behavior, not implementation

Check 1

Break the behavior

→ the test must fail

Still passes? It proves nothing. Usually a loose assertion, or an expected value computed by the code under test.

Check 2

Change the internals, keep the results

→ the test must pass

Fails? It's pinned to the implementation, and it will break on every refactor.

Pinned to implementation
def test_post_video(): db = Mock() post_video(db, clip) db.insert.assert_called_once()
Tests what a user sees
def test_followers_see_new_video(): post_video(app, clip, by=alice) assert clip.id in feed(app, for_user=bob)

Take expected values from the requirement, never from the code you're testing.

When is testing complete?

Never fully. You stop when the risk left is low enough to ship.

Exit criteria teams use

  • Every requirement has a testa traceability matrix maps them
  • Each input class and boundary is covered
  • The riskiest flows get tested deepestlogin, payment, posting
  • Coverage and mutation score meet the target
  • New bugs per day have flattened
  • No open critical bugs

A/B test: how much should one like change the feed?

Guardrails: "not interested" taps, reports, uninstalls

Rules for a fair test

  • Random split, so the groups are alike.
  • Pick the metric before you start.
  • Guardrails too: crashes, reports, latency.
  • Run long enough for the difference to be real, not noise.
  • Ramp up: 1% → 10% → 50% → 100%.

Why would a product make one signal easy and the other hard?

Product

A like keeps you watching. "Not interested" shows you less. Friction lowers how often people use it.

Signals

Most "no" is implicit: fast swipes, short watch time. An explicit "no" is rare, strong, and easy to tap by accident.

Testing

A/B tests count what is easy: watch time, likes. Regret is hard to measure, so the version that hides "no" can win.

What your test can't measure, your product will optimize away.

The hardest instruction is "don't"

Every rule you give an agent is a negative prompt: don't log emails, don't touch the tests, don't add sleep().

1. Ask

Say it in the prompt

"Don't log user emails."
2. Remind

Write it in CLAUDE.md or a skill

- Never log PII
3. Review

Ask a reviewer agent to check

"Does this log PII?"
4. Enforce

A test, lint rule, or hook that fails

assert email not in logs
Rules fadeThe longer the context, the less a line from the start counts.
"Don't" leaves no traceA slip looks like normal code. Nothing prompts a second look.
A reviewer is another rollIt can miss the same slip, on a different run.

Three tests worth investing in

Pick this if only one

End-to-end

Does the real feature work?
Drive the running app the way a user would.
Best forUser flows: post a video, like, comment

Property-based

Does a rule hold for any input?

Does new behave like old?
Feed both the same inputs and compare outputs.

Property-based: state a rule, let the machine attack it

from hypothesis import given, strategies as st @given(st.lists(st.sampled_from(["like", "unlike"]))) def test_likes_never_negative(taps): post = Post(likes=0) for tap in taps: post.tap(tap, user="u1") assert post.likes >= 0
Falsifying example: taps=['unlike'] AssertionError: assert -1 >= 0
Hypothesis tried hundreds of tap sequences, then shrank the failure to the smallest one: unlike a post you never liked.
Round-tripdecode(encode(draft)) == draftSaving and reopening a draft loses nothing
Invariantpost.likes >= 0True after any sequence of actions
Idempotentupload twice == upload onceA retry never double-posts
Equivalencefast_rank(feed) == slow_rank(feed)The optimized code matches the simple, correct one
Why it suits agents: the rule comes from the spec, not from the agent's code, so it has different blind spots.
Tools: Hypothesis (Python), fast-check (JS/TS), proptest (Rust)

Differential: the old system is the oracle

Example: an agent rewrites the comment service from Python to Go. Nothing should change.

No spec needed

Old behavior is the answer key, even where the docs drifted.

Normalize the noise

Ignore whitespace, ids, and times, so only real differences show up.

Keep an approved list

Intended changes go on a list. Everything else is a bug until shown otherwise.

Prove it works, on the real thing

Doesn't count

  • "It compiles"
  • The agent says it's done
  • Old or cached output
  • The file changed
  • Unit tests passThey show branch behavior, not that the bug is gone

Counts

  • Run the feature
  • Read the actual value
  • Check on the same surface as the bug
  • Paste the output: failing, then passing
  • A script anyone can rerun
When a check fails, first doubt how you looked, then the system.
Never hand the human a check the agent could run itself.

$ pytest tests/test_likes.py FAILED test_unlike_without_like assert post.likes >= 0 # got -1 # fix: only unlike if this user liked it $ pytest tests/test_likes.py 1 passed in 0.04s

Rules for the test

  • Don't change the test to match wrong code.
  • Don't weaken an assertion without a reason.
  • Prefer no new test over a bad test.
  • Show both runs: failing before, passing after.

Several models attack the diff

A finding counts only if it comes with a run: a failing test, a repro script, or command output.

Crash on an empty captionfailing test
Retry posts the video twicerepro script
Might be slow at scaleno run, dropped

Other agents still make mistakes. So a verdict rests on a run, not an opinion.

Keep the verifier honest

Out of reach

A change can't edit its own checks

Review rules are read from the main branch, never from the PR.

Fresh

Review the commit you ship

A pass on an older commit means nothing.

No retry-until-green

Flaky tests get fixed or deleted

No sleeps, no skips. Find the cause, or delete it and write down why.

Escalate

Three strikes, then a human

After three failed rounds the agent stops and asks.

Roll out slowly

Off → observe → enforce

A new gate first only logs what it would block, to catch false alarms.

Learn

Test the checks too

Score them on past bugs that got reverted. Every miss becomes a new rule.

Takeaways

  1. 1
    Coverage shows what ran, not what was checked. Mutation testing shows whether tests catch bugs.
  2. 2
    Some things only users can test. Use A/B tests with guardrails.
  3. 3
    Agents are confidently wrong. A second agent is one more sample, not proof.
  4. 4
    Turn every "don't" into a check. Prompts can slip. Tests, lint rules, and hooks don't.
  5. 5
    Invest in E2E, property, and differential tests. They are hard to fool.
  6. 6
    Prove it on the real thing. Red first, then green, and test behavior, not internals.
